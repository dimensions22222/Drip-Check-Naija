# Architecture and trust boundaries

The avatar catalog holds typed wearable metadata and independent character-compatible selections. The avatar renderer composes layers in a fixed z-order. The app shell runs in local/demo mode without credentials; when configured, a typed Supabase client provides email Auth, owner-scoped profiles/avatars/outfits, public active catalogue reads, and owner-only inventory reads. Cloud outfits are cached separately from local drafts and never replace them on sign-in.

Drip City reuses the saved Studio look and `AvatarRenderer`. Its Phaser map is a lazy-loaded, single-player scene with local movement only. Public discovery and showcases use curated Supabase views; authenticated follows, likes, publishing, and avatar visibility use database RPCs/owner-scoped writes. Public avatars are opt-in, saved outfits remain private unless explicitly published, and local drafts are never uploaded automatically. The new social schema is in `supabase/migrations/202611180001_drip_city_social.sql`; see [DRIP_CITY.md](./DRIP_CITY.md) for movement, RLS, demo behavior, and future multiplayer requirements.

The Supabase schema keeps RLS enabled. Browser clients can read only their own profile, avatar, inventory and outfits; active catalogue rows are public and read-only. Outfit item IDs are checked by a database trigger against active catalogue slugs, slots, and character compatibility. Profile column grants exclude level and XP. No service-role key belongs in Vite variables.

No trusted game backend, economy, inventory grants, purchases, battle submission, voting, scoring, rewards, live multiplayer, chat, or moderation operations are implemented. Existing battle and voting UI remains demo-only. Future sensitive mutations must run in trusted server-side RPC/API transactions with ownership checks and validation. The client must never submit a balance, price, result, or arbitrary asset URL as authority.
